# Demo 08 — Integrity monitoring: a SHA-256 manifest and an HMAC seal

**Topic:** File integrity monitoring (the logic behind Tripwire / AIDE), application allowlisting, protecting
the "expected values" · **Week:** 2 · **Book:** Viega & Messier, Recipe 12.2 (change detection; the book's CRC32
is updated here with SHA-256), Recipes 6.1 and 6.10 (digests and HMAC)

## What it shows

When malware plants itself on a system, it usually **leaves a trace**: it patches a library, drops a new file,
deletes a log. An integrity monitor writes every file's cryptographic digest, from its "known good" state, into
a **manifest**, then recomputes and compares it later.

| Step | What happens | Lesson |
| --- | --- | --- |
| 1 | A SHA-256 manifest is written for the four files under `output/monitored/` | The baseline |
| 2 | The manifest is **sealed** with HMAC-SHA256 using a random key | The expected values need protecting too |
| 3 | Verification with nothing changed: everything is `OK` | |
| 4 | Simulation: a line is added to one file, one is removed, a new one is dropped | `CHANGED`, `DELETED`, `NEW` |
| 5 | The "attacker" rewrites the manifest too: the monitor is fooled | An unprotected local reference value is a weakness |
| 6 | Seal verification fails: the manifest was changed by someone without the key | HMAC cannot be produced without the key |

SHA-256 and HMAC work on both platforms: OpenSSL on Linux, the operating system's BCrypt library on Windows
(`common/cen429_kripto.h`). The HMAC comparison is **constant-time**.

## Running it

First build all the demos once (inside the `code/` folder): Windows `.\build.ps1` ·
WSL / Linux `./build.sh`. Then, inside this folder:

| Environment | Command |
| --- | --- |
| Windows (PowerShell) | `.\demo.ps1` — or double-click `demo.cmd` |
| WSL / Linux | `sh demo.sh` |

## Why it's safe

- Every file is generated by the demo script with **synthetic** content under this folder's `output/`; the
  "attack" only ever touches files we generated ourselves.
- The program only looks at **regular files at the top level** of the given folder: it never descends into a
  subfolder, never follows a symbolic link, and never modifies any file (it only writes the manifest and the
  seal).
- The seal key comes from the operating system's secure random number generator and is regenerated on every
  run; it protects no real secret.

## Try it yourself

- In step 4, change only a file's **modification time**, not its content (`touch output/monitored/config.conf`).
  What did the monitor say? Why?
- What's the risk of keeping the seal key in the same folder as the manifest? Where should it really live
  (a read-only medium, a separate server, a hardware module)?
- Recipe 12.2 uses CRC32. Why can an attacker easily forge a CRC32 match, but not a SHA-256 one?
